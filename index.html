⚡ The 10 must-knows — memorise first

  1. GFS 2003 → HDFS 2006. HDFS = open-source GFS in Java. master→NameNode, chunk→block, chunkserver→DataNode.
  2. NameNode = brain. Metadata (namespace + block→DN map) in RAM. On disk as FsImage (snapshot) + EditLog (WAL).
  3. DataNode = stores block bytes. Sends heartbeat (3 s) + block report (6 h).
  4. Block = 128 MB, replication = 3. Last block not padded → 1 GB = 8 blocks.
  5. Control plane vs data plane: NameNode gives locations only; data flows client↔DataNode directly, never through the NameNode.
  6. Secondary NameNode ≠ standby. It only checkpoints (merges EditLog→FsImage).
  7. Rack-aware (RF3): R1 local, R2 other rack, R3 same rack as R2 → survives any 1 rack failure.
  8. Write pipeline: client→DN1→DN2→DN3, ACKs reverse. Read: ask NN → read DN direct.
  9. HA kills the SPOF: Active + Standby NameNodes + Journal Nodes + ZooKeeper/ZKFC + fencing.
  10. 4 limits: small-file problem (150 B/file heap), no random writes, high latency (50–200 ms), NameNode SPOF.

📉 Why conventional file systems fail at petabyte scale (§3.1)

The 3 breaking points

  • Single-machine capacity — NFS/SAN lean on a finite set of controllers; one host can't hold PBs. Must spread across a cluster.
  • Throughput — 1 disk ≈ 50 MB/s → reading 1 PB from one disk = ~230 days. Across 1,000 disks in parallel → ~5 hours.
  • Failure is normal — a few-thousand-node cluster sees ~3 node failures/day. A system that treats failure as exceptional spends most of its time recovering. Design for failure as the expected case.
Data-locality idea (Ch.1 callback): move computation to the data, not data to the computation — the founding principle behind both GFS and HDFS.

🔵 The Google File System (§3.2)

Published by Ghemawat, Gobioff & Leung, SOSP 2003 — one of the most-cited systems papers ever (14,000+ citations). Purpose-built for Google's workload; deliberately not POSIX-compliant. Its central bet: workload-specific design beats general-purpose design at extreme scale.

Workload GFS was built for: files are huge (GB–hundreds of GB) · access is sequential reads + sequential appends · random writes essentially absent · write-once, read-many · many concurrent readers, not concurrent random writers.

The 6 GFS design decisions ★

  1. Large chunk size (64 MB) — vs 4 KB blocks → far less metadata, less client↔master chatter, direct TCP streaming.
  2. Centralised in-memory metadata — master holds namespace, chunk→file map, locations, ACLs in RAM; 1 PB ≈ 16M chunk entries fits.
  3. No data caching — streaming reads would evict cache before reuse; rely on OS buffer cache.
  4. Write-by-append — optimised for atomic append (logs, crawl output, index segments).
  5. Replication, not RAID — 3 chunkservers/chunk; master re-replicates on failure.
  6. Relaxed consistency — weaker than POSIX; concurrent writes can be "defined but inconsistent"; apps cope with unique IDs + read-time dedup.

GFS architecture — 3 components

  • 1 GFS master — all metadata in RAM; control plane only, never touches data bytes.
  • Chunkservers — store chunks as plain Linux files; verify checksums on every read; no memory cache.
  • Clients — GFS API (not POSIX); ask master for chunk handles + locations, then talk directly to chunkservers; cache locations briefly.

Master ↔ chunkserver: heartbeat (every few sec) + chunk report (which replicas held → rebuild map after restart).

The one big idea: separate the control plane (master/metadata) from the data plane (direct client↔chunkserver transfer) — so one master is never the bottleneck.

🟢 HDFS architecture (§3.3)

Open-source Apache reimplementation of GFS in Java. Built at Yahoo! by Doug Cutting & Mike Cafarella (from the Nutch crawler), donated to Apache in 2006. Renames only: master→NameNode, chunkserver→DataNode, chunk→block.

NameNode — the master / "index"

All metadata in RAM (~150 B/file + 150 B/block; 1M files ≈ 300 MB heap). Two on-disk structures:

  • FsImage — full point-in-time snapshot of the namespace.
  • EditLog — write-ahead log of every mutation since the last checkpoint.

Startup: replay EditLog onto last FsImage → current state. Checkpointing merges them so EditLog never grows forever.

⚠️ Block locations are NOT persisted — they're rebuilt at startup from DataNode block reports, avoiding stale-location bugs after failures.

5 responsibilities ★: namespace · block mgmt (+re-replication) · access control · lease mgmt (who may write) · load balancing (Balancer).

DataNode · Secondary NN · Blocks

DataNode — stores block bytes on local disks; serves reads/writes direct to clients. Commodity HW (2024: 12–24 disks × 8–18 TB). Sends:

  • Heartbeat (3 s) — "alive"; miss >10.5 min → marked dead → re-replication.
  • Block report (6 h / on startup) — full replica list.
  • Block scanning (~3 wk) — checksum every block; corrupt → re-replicate from a good copy.
⚠️ Secondary NameNode ≠ standby. It only checkpoints (EditLog→FsImage) to shorten restart. Failover needs HA. Runs hourly or every 1M EditLog txns.

Blocks: default 128 MB (was 64 MB), stored 3×. Last block not padded → 1 GB = 8 blocks, not 9.

✏️ Diagrams to draw — the biggest marks

Say: NameNode holds metadata in RAM (FsImage+EditLog); Secondary NN only checkpoints; client gets locations from NN (①), then moves data direct to DataNodes (②). NN never touches block data; DNs report via heartbeat + block report.

Say: create() → NN grants lease; addBlock → NN returns rack-aware DN list; data streams client→DN1→DN2→DN3 in 64 KB packets (each DN writes + forwards); ACKs travel back; NN told on completion.

Say: open() → NN returns DN list ordered by proximity (data locality); client reads direct from the nearest DN; checksum each 512 B, retry on mismatch. NameNode is out of the data path.

Say: R1 = writer's node (low latency); R2 = different rack (survive a rack loss); R3 = same rack as R2 (save cross-rack bandwidth).

Say: Active writes edits to the Journal Node quorum; Standby replays them (~ms behind). ZooKeeper + ZKFC detect failure & elect the Standby. Fencing kills the old Active first so both never write at once (split-brain).

🔁 Replication & fault tolerance (§3.4)

Rack-aware placement ★

Servers sit in racks (20–40 nodes on one top-of-rack switch); a switch/PDU failure kills the whole rack. So RF=3 places:

  • R1 — writer's node (or random) → low write latency
  • R2 — a different rack → survive a rack failure
  • R3 — same rack as R2 → less cross-rack traffic
Result: a single rack failure can never destroy all replicas — ≥1 always survives.

Failure detection & re-replication

DN misses heartbeats past threshold → NameNode finds every block it held, and if replicas < factor, schedules re-replication (a surviving DN copies the block to a new DN).

  • Priority by urgency: blocks with only 1 surviving replica first, then 2.
  • Big maintenance windows → NameNode throttles re-replication to avoid saturating the network.
Write durability: a success-ACK'd write is on ≥ r DataNodes; losing up to r−1 at once loses nothing.

🔀 Read & write paths in words (§3.5)

Read path

  1. open() → RPC NameNode for first blocks' locations.
  2. NN returns DNs ordered by proximity (same node → rack → other racks).
  3. Client connects direct to closest DN, streams over TCP.
  4. Checksum each 512 B (CRC-32C); mismatch → report + retry another replica.
  5. Block boundary → ask NN for next blocks; close() at end.

Write path ★

  1. create() → NN entry + write lease.
  2. addBlock → NN returns rack-aware DN list in pipeline order.
  3. Build pipeline client→DN1→DN2→DN3.
  4. 64 KB packets flow down; each DN writes + forwards; ACKs back up.
  5. All 3 ACK → NN records block; close() releases lease.
Pipeline failure: failed DN dropped, new pipeline built excluding it, unconfirmed packets re-sent; write succeeds if ≥1 DN survives; NN re-replicates later.

🛡️ HDFS High Availability (§3.6)

Problem: the original NameNode is a Single Point Of Failure. Yahoo! 2011 — a NameNode outage stranded 42,000 DataNodes; recovery took 30–60 min. Fix (Hadoop 2.0, 2012): Active + Standby NameNodes with automatic failover.

ComponentRole
Journal Nodes (≥3, quorum)Shared, fault-tolerant edit log. Active writes every mutation; Standby continuously replays → only a few hundred ms behind.
ZooKeeper (≥3) + ZKFCLeader election + health monitoring. Each NameNode runs a ZooKeeper Failover Controller; Active's session expiring triggers election → Standby promoted.
FencingPrevents split-brain (both Active → divergent metadata). Fence the old Active first: SSH stop / remote-kill or STONITH hardware.

☁️ Beyond HDFS: cloud object storage (§3.8)

How S3 / GCS / ADLS differ

  • Flat namespace keyed by path-string (prefixes mimic folders); objects up to 5 TB.
  • Unlimited, auto-scaling — no NameNode heap limit, no manual replication, no DataNodes.
  • Cheap + simple — ~$0.023/GB/month, no servers or HA to run.
  • Trade-off: storage/compute separated → every read is a network hop (no data locality), but 25–100 Gbit/s networks make it minor.

The big shift ★

From tightly-coupled storage-compute (HDFS: add compute only by adding storage) to loosely-coupled (S3 + cloud compute: scale Spark 10→1,000→10 nodes without moving a byte).

Elasticity is the reason cloud object storage displaced on-prem HDFS for new builds. HDFS still lives in own-data-centre shops.

📚 Case study — Yahoo! Hadoop (2006–2011) (§3.9)

  • Scale: 1,000 → 42,000 nodes; ~100 PB in HDFS; tens of thousands of MapReduce jobs/day; ~2–3 DataNode failures/day — exactly the GFS prediction.
  • NameNode bottleneck: 50B blocks filled 64 GB heap; 90-min restarts → solved with HDFS Federation.
  • Small files: millions/day → automated SequenceFile compaction (~1,000× smaller namespace).
  • Contributed to Apache: HDFS Append, Hadoop Security (Kerberos), HDFS HA, and YARN.
  • Lesson: invest in HA before the outage; manage NameNode memory and small files actively.

❓ Self-test — click to reveal (SQ3.1–3.14)

SQ3.1 3 reasons NFS can't do 500 PB?
Capacity (finite controllers, no horizontal scale) · Throughput (can't parallel-scan PBs) · Fault tolerance (~3 fails/day treated as exceptional → always recovering).
SQ3.2 GFS chunk? Size & why not 4 KB?
Fixed unit a file splits into; 64 MB. Big → less metadata, less client↔master chatter, sustained direct sequential I/O.
SQ3.3 Why metadata in RAM? Ceiling?
Sub-ms lookups. Ceiling = chunk entries that fit in RAM; 1 PB ≈ 16M entries @ 64 MB → fits, so master ≠ bottleneck.
SQ3.4 NameNode? 5 jobs? If killed?
Master/metadata server. Jobs: namespace, block mgmt, access control, lease, balancing. Killed → whole cluster inaccessible (bytes exist but unreachable).
SQ3.5 Secondary NN vs standby?
Secondary is NOT failover — only checkpoints (EditLog→FsImage) to bound restart time. Failover = HA.
SQ3.6 Rack policy? After rack fails?
R1 local, R2 other rack, R3 same rack as R2. Any 1 rack fails → ≥1 replica survives → goal met.
SQ3.7 Trace write. Where data sent? Hops?
create()+lease → addBlock → pipeline client→DN1→DN2→DN3, 64 KB packets, ACK back. Data sent at packet step, 3 DN hops; ACK'd only after all 3 write.
SQ3.8 Heartbeat vs block report?
Heartbeat (3 s) = "alive", miss >10.5 min → dead + re-replicate. Block report (6 h) = list of replicas → NN builds block→DN map.
SQ3.9 200M files × 1 block, 300 B/pair → heap?
200M × 300 B = 60 GB heap — independent of data volume = the small-file problem.
SQ3.10 Why no random writes?
Only new-file writes + appends; blocks immutable → no cross-replica write coordination → simple consistency. Updates → HBase.
SQ3.11 HA? 3 extra components?
Active + Standby NN. Journal Nodes (≥3) shared edit log · ZooKeeper/ZKFC (≥3) election + health · Fencing stops split-brain.
SQ3.12 Split-brain? Fencing? 2 ways?
Both NNs Active → divergent metadata. Fencing stops old Active first. Ways: SSH kill · STONITH hardware.
SQ3.13 HDFS vs S3 (4 dims)?
Locality: HDFS local / S3 network hop · Ops: HDFS heavy / S3 managed · Ceiling: HDFS ~100M files / S3 unlimited · Cost: HDFS capital / S3 $0.023/GB/mo.
SQ3.14 1M×200 KB files/day → heap full. Cause + 2 fixes?
Cause = small-file problem (~150 B/file heap). Fixes: SequenceFiles/HAR compaction · batch/append into big files (CombineFileInputFormat).
AP3.1 50 PB, RF3, 128 MB — key answers
Raw = 150 PB; blocks ≈ 419M; DNs @200 TB ≈ 768; heap ≈ 63 GB (fits 128 GB); RF3→2 saves 50 PB but tolerates only 1 loss.
